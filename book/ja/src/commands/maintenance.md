# メンテナンス

```sh
sekai --store ./sekai-store gc --dry-run
sekai --store ./sekai-store gc
```

`gc` は、どのスナップショットからも参照されていない孤立した CAS Blob を回収（削除）します。
計画（プランニング）フェーズは読み取り専用です。適用フェーズでは、ファイル削除（unlink）を行う直前に最新メタデータと照合して削除候補を再検証します。そのため、CLI の1回の実行で両フェーズを処理する場合でも、安全な2フェーズ構成（計画作成後に適用）が維持されます。

`gc --dry-run` は計画内容のみを表示します。`--timing` と組み合わせることも可能ですが（計画フェーズの時間が計測され、`apply_ms` は `0` となります）、適用フェーズが存在しないため `--progress` との併用はできません。

GC が削除するのは孤立した Blob のみであり、メタデータを削除することはありません。スナップショット自体の削除には `prune` コマンドを使用します（保持対象スナップショットへのレコード統合後、`gc` で不要 Blob を回収）。

`backup` が実行中の場合、`gc` は安全のため実行を拒否してエラーを返します。バックアップ処理はメタデータ行をコミットする前に先行して Blob を書き込むため、その合間に GC を実行してしまうと、次のコミットで必要となる Blob を誤って削除してしまうおそれがあるためです。エラーメッセージには、ストアのルートにあるマーカーファイル `backup.inflight` が示されます。実際にバックアップが実行されていない場合（前回の異常終了などでファイルが残ってしまった場合など）に限り、このマーカーファイルを手動で削除してください。なお、古いマーカーファイルが残っていても `backup` 自体の実行が妨げられることはありません。詳細については [ADR-0011](https://github.com/tmcjapan/sekai/blob/main/docs/adr/0011-backup-run-marker.md) を参照してください。

## スナップショットの整理・削減 (Prune)

```sh
sekai --store ./sekai-store prune --keep-last 10 --dry-run
sekai --store ./sekai-store prune --keep-last 10
sekai --store ./sekai-store prune --before @stable
```

`prune` は不要になった古いスナップショットを削除します。
保持条件は、最新の `--keep-last N` 件と `--before` 以降の条件の積集合（AND条件）として判定されます（少なくともどちらか一方の指定が必須です）。結果として保持スナップショットが 0 件になってしまうような指定をした場合は、誤ってストア全体を空にしてしまうのを防ぐため、エラーを出して中断します。

削除処理は古いスナップショットから順に畳み込み（fold）を行います。削除対象となったスナップショットが持つ有効なレコードは次の保持スナップショットへと統合され、すでに上書き済みの不要なレコードのみが破棄されます。そのため、残されたスナップショットから復元されるデータ内容は完全に維持されます。削除されたスナップショットに付与されていたタグも同時に削除されます。

`prune` は Blob の削除（unlink）を直接行いません。参照されなくなった Blob を回収するには、`prune` の実行後に `gc` を実行してください。
`--dry-run` を指定すると、削除予定のスナップショット一覧のみが表示されます。

スナップショット、メタデータ、Blob など、ストア全体を含む完全な二次バックアップを作成したい場合は、ストアディレクトリ全体をそのまま外部ストレージ等へコピーまたはアーカイブしてください。各コマンドにおけるディスク書き込みはクラッシュに強い順序（Blob の書き込み → メタデータのコミット → 不要ファイルの削除）で行われるため、稼働中にコピーされたストアでもデータの一貫性が保たれます。
